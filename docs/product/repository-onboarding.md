# Repository onboarding

Operator-approved repository maintenance. Source and isolated conformance do not
activate these changes; the existing composed acceptance and Platform activation
procedure establishes the installed operating version.

Workspace Registry coordinates repository onboarding. Repository Control owns
GitHub creation, linkage, provider management and technical source controls.
Both surfaces use the same custody records, Intake decisions, source setup and
Inventory activation. There is no separate Console-owned admission decision.

## Operator path

1. Create or link the repository in Repository Control. Its successful receipt
   confirms that provider operation, not readiness for project work.
2. Choose **Continue onboarding in Registry**, or open Workspace Registry,
   **Onboard workspace item**, then **Repository**. Select an already verified
   repository. Arrival from Repository Control selects its immutable provider ID
   automatically; details are read again from the custody owner.
3. **Continue onboarding** opens the existing repository details form. Review
   purpose, how source changes are checked and any required separate Security repository.
   **Record for setup and review** retains the proposed registration. Missing
   owner controls can then be prepared through **Review repository setup**.
   Existing valid controls are reused. See [Repository setup](repository-owner-setup.md).
4. After source controls are verified, review **Approve for activation**. The
   owner enforces its actual prerequisites; selecting the option is not approval
   evidence or activation. Preserve the original request if acknowledgement is lost.
5. **Review activation** opens Registry's existing eligible-record view, filtered
   to this repository. Review the actual prepared candidate and complete the
   existing activation workflow. Only current active Inventory establishes
   completed repository onboarding.

The onboarding view distinguishes the recorded workspace decision, verification
of source controls for that decision, and current activation. Unavailable or
contradictory records display a retry and keep project use blocked. History and
previous receipts do not establish current readiness. An already suspended or
retired Inventory record directs the user to its existing Registry lifecycle
record; it does not offer duplicate onboarding or fresh activation.

## Use gate

Before completed onboarding, inspection, history, approved source-control setup,
withdrawal and original-outcome recovery remain available. Normal project source
work and Delivery repository linkage require current active readiness.

OOS reuses the existing Inventory/WGCF readiness authority before resolving a new
Proposal repository dependency, preparing a repository-backed disposition or
handoff, and preparing/publishing a Prototype target. A creation/link receipt alone
cannot resolve project readiness. Backend checks apply independently of browser
controls and repeat before new source publication. Existing Delivery Catalog and
ordinary-source identity checks retain their current active-source requirements.
Stale, suspended, retired or unavailable authority never becomes permission to use
a repository. Recovery reads preserve original requests; they do not grant a new
source action.

Application verification is separate from onboarding. Early work can retain the
existing `unconfigured` application-verification posture; source review and
validation controls still apply. This flow introduces no mandatory application
test suite, deployment or CI policy beyond the owner's existing requirements.

## Records and project routes

Repository records describe source custody. Product records describe complete
applications/services; component records describe separately managed supporting
parts. Repository onboarding does not require creating all three.

Proposal reuse searches current Registry records, including internal project
registrations, using bounded pages and explicit partial-result guidance. A failed
Registry read cannot fall back to example or historical repositories.

Repository readiness does not grant publication or private-source export. The
existing public Studio route requires fresh public provider readback for internal
project sources, with exact provider identity. Private/internal, archived,
mismatched or unavailable sources cannot be published through that route.
Private-capable Delivery continues to use installation-private registrations and
its separately approved source permissions. No automatic model context or public
Studio publication is authorized by onboarding.

The old prototype-local **Repository Admission Run** and its writer are retired.
Historical demonstration receipts remain readable and explicitly labelled; they
cannot register, approve, activate or unlock a repository.

## Form and outcome usability

The details form uses the verified custody identity and available creation
description automatically. On reopening, answers from the latest completed,
matching, in-scope request can fill a pristine form. Edited drafts are not replaced,
pending requests are not treated as completed answers and no security choice is
guessed. Shared check IDs and other recorded specialist settings are retained;
source bindings are revalidated by the existing owner workflow before approval.

Review shows human-readable decisions, repository, purpose, security responsibility
and source-check approach. Category/role codes, provider IDs and source digests
remain inspectable in technical details. A completed setup decision offers
**Review repository setup**; a completed approval offers **Review activation**.
Neither outcome is labelled as completed repository onboarding. Pending, blocked,
rejected and cancelled requests explain their actual state and next action.

Loading history, preparing review and updating the original request use shared
waiting feedback. A failed read offers a retry without replacing failure with an
empty successful history. Browser waits respect the existing owner read/command
budgets. An interrupted submission keeps the original request ID and reviewed
decision; check the original outcome before another submission. Leaving this
uncertain result does not cancel the owner operation.
