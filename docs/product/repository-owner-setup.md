# Repository setup

This is the primary Console procedure for the staged trusted owner-control
workflow. Source implementation is not operating activation. Exact composed
Security acceptance, Platform commissioning and browser/recovery proof remain
required before normal use. The current adapter qualifies public synthetic
repositories on `main`, not private/client projects or arbitrary toolchains.

## Operator path after commissioning

1. Open **Workspace Registry → Onboard workspace item → Repository**, or use
   **Continue onboarding in Registry** from the created/linked repository.
   Complete the existing proposed registration decision, then open **Review
   repository setup** from its onboarding details. See the coordinated
   [Repository onboarding](repository-onboarding.md) procedure.
   OOS verifies current proposed or admitted source-only classification,
   absence from active/retired Inventory and exact canonical custody;
   page-local labels do not grant eligibility.
2. The dialog loads retained requests and the current verification plan when
   applicable. An original pending request is recovered even
   when it is outside the bounded history page. Resume it rather than creating
   another branch or request after a lost acknowledgement.
3. For genuinely new setup, review the source controls and the explicit optional-CI
   choice. The service derives the bounded source-validation profile; application
   verification starts as `unconfigured`. No application test description,
   guessed executable or finished application is needed. Existing independent
   profiles and controls are inspected and preserved. Active registration still
   requires the existing PR-control policy; choosing no new workflow is suitable
   when the repository already has the applicable workflow.
4. Inspect the finite trusted plan and all displayed source as inert text.
   Existing README and independent owner controls are preserved. Optional CI
   requires a separate explicit approval for the exact displayed workflow,
   plus the actual App/installation permission. Accept the exact preparation
   contents with **Confirm setup request** (or **Confirm verification change**)
   to retain one immutable request. The preparation digest stays available in
   **Technical details**.
5. Complete existing controls use the non-source canonical checkout action: no
   source-write credential, source branch or dummy PR. Legacy public reads issue
   no read token; native private checkout reports its scoped read token and
   successful revocation. A changed profile requires a fresh
   inspection, never silent replacement of independent owner policy.
   Missing review controls use the same finite trusted source plan, including
   an admitted owner still absent from Inventory. Only absent control files and
   append-only missing AGENTS review guidance may change; application files,
   valid profiles and independent controls are preserved. Incomplete independent
   review policy blocks rather than being overwritten. Optional bootstrap CI
   does not waive the existing active-Inventory PR-control requirement.
6. A source plan uses the existing **Source access** panel with its distinct
   `trusted-owner-bootstrap` purpose. Inspect finite paths, plan/template
   digests, exact current Intake binding, actual provider identity and expiry.
   **Prepare source access**, review the displayed repository, branch, allowed
   files, reviewer, workflow permission and expiry, then **Approve source access**.
   Provider identity and binding digests remain in **Technical details**.
   Continue with **Start repository setup** after approval is confirmed.
7. **Review proposed files**, then **Accept reviewed files**. This accepts only
   the inspected contents bound to their exact digest.
   Validate/publish through Gary, approve the exact retained PR head as the
   accountable human, merge, then verify merged readback, credential revocation
   and owned-resource retirement. The durable canonical checkout is preserved.
8. Return to the existing separate Intake admission, active Inventory and
   Catalog workflows. Completed repository setup does not itself admit a repository,
   execute application tests, build the app or activate a runtime.

## Recovery and withdrawal

The modal header and selected action show what is happening while the service
responds. A result appears after a confirmed response; the selected request and
its next action describe the durable workflow state. Publication, review and merge
can still need further reconciliation; a returned status is not a claim that
application tests passed. The retained pull request opens separately for review.

Browser waits are bounded to 15 seconds for each read and 135 seconds for each
command response, allowing the owner's 12-second read and 120-second command
budgets plus transport time. Ending a browser wait does not cancel work already
accepted by the service. An interrupted command shows **Outcome not confirmed**
and blocks further changes until **Check original request** succeeds. Draft
fields and the original request ID, approval, command and timestamp are retained
in the current dialog for retry. Reopening recovers the service's retained request;
it does not create a replacement. If source-access approval or closure is
interrupted, use **Check original access request** before continuing. A failed
read offers a local retry instead of implying there are no requests.

For an active repository, open **Application verification** from Repository
Control. The title names the task; the repository name appears underneath.
The service checks current source-only eligibility and reads the reviewed plan
before showing editable checks. Ineligible or unavailable source keeps the editor
closed, with failure guidance and a retry for temporary read failures. Existing
pending requests resume without a replacement preparation. Opening this read-only
check creates no source request, credential or application result. **Previous requests** lists both setup and verification requests by
type, status and update time. **Open request** inspects or resumes the exact
retained request; its ID and service details remain under **Technical details**.
After a finished request, **Start new verification change** returns to the plan
form while preserving that earlier request. Refresh requests rereads status;
it does not create or execute a change. Completed request status describes the
source workflow, not passed application tests.

Refresh and reopen the original owner request after reload. Publication,
review, merge, existing checkout and cancellation reuse their original retained
command and timestamp. Unknown source application uses accepted-source recovery,
not another draft. Terminal requests stay terminal.

**Withdraw request** opens an inline reason field rather than interrupting the
primary setup action. Before source is committed, explicit reasoned cancellation stops unissued
preparations without inventing a provider revoke, revokes approved/uncertain
access through Platform, and retires only proven pristine source resources.
Unavailable authority is not evidence that no credential exists. Unknown
cancellation reconciles its original command. Committed, dirty, remote or
uncertain source must be recovered/reviewed, not discarded as an unapplied draft.

Missing current classification/custody, permissions, applicable profile or exact
readback stays blocked at its named owner. No fixture success, CLI-only fallback,
new repair story, source-scope waiver or automatic admission substitutes for it.

`record_authority_unavailable` identifies the Platform-owned canonical record
refresh dependency. Restore its approved fresh snapshot, then retry the exact
setup; this is not an instruction to admit the owner or replace a retained
request. The Console maps only this known bounded code to fixed safe guidance.
Unknown, malformed or oversized upstream errors remain opaque; backend message
text, diagnostics and credentials are never displayed.

## Visibility and project-type scope

Creation and linking retain the explicitly selected visibility, including private
and internal repositories. Their forms explain that setup requires approved
source access on `main` and eligible source-only authority. The service checks
that access before preparation. The accepted legacy adapter remains public-only;
the unpublished native private-source extension requires its coordinated
activation. Creation/link success is not proof of development eligibility.
Never change a repository to public to bypass an unavailable source connection.

Documentation and notes may use source controls without an application runtime
or a finished app-test plan. Manual application checks and Delivery non-source
completion reuse their existing reviewed workflows; writing versioned documents
is still source work. A no-source Delivery outcome does not require a dummy
repository. Optional CI generation does not waive active registration policy.

## Private-source boundary — approved, implementation in progress

The remaining private-source gap needs coordinated OOS, Platform and Security
qualification. The preferred first scope is exact-repository, short-lived
read-only inspection of the known owner-control files, using Platform-held
GitHub App authority and canonical custody. Keep metadata-only account reading
separate from source reading. Do not broaden the metadata reader's all-repository
permission or borrow ambient Desktop/CLI credentials. Source remains private;
no private content enters public Studio records or automatic model context.

The current Security boundaries are documented in
[repository verification maturity](https://github.com/mfshaf7/security-architecture/blob/main/docs/reviews/components/2026-11-03-repository-verification-maturity.md)
and the separate
[account metadata reader review](https://github.com/mfshaf7/security-architecture/blob/main/docs/reviews/components/2026-11-03-account-repository-reader.md).
The first retains public synthetic main-source qualification; the second limits
the account-wide grant to Metadata read and keeps source-content permissions
separate. An early UI warning does not close this remaining capability gap.

The operator approved the exact credential issuer/binding, repository
selection and file scope, read retention, expiry/revocation and recovery below. Qualify
private source on the existing `main` route first; other default branches and
private model authoring require their own explicit scope and evidence. This is
an approved implementation boundary, not an activated permission or a completed capability.

Approved first implementation boundary:

- OOS extends its existing repository-owner-bootstrap preparation/source reader;
  Platform extends its existing source-App issuer and protected credential
  custody. Security reviews that exact delta. The Console keeps the existing
  preparation, source review and recovery surfaces.
- The subject is one private GitHub organization repository on `main`, with
  successful canonical custody and current source-only Intake. Its immutable
  provider ID and account are verified before issuing read access. Internal
  visibility, other default branches and model authoring are outside this first
  qualification scope.
- Reuse the installed source App, with a repository-scoped token reduced to
  Metadata read and Contents read, at most the existing one-hour lifetime and
  revoked after inspection. No account-wide source token or browser credential.
  GitHub permissions are repository-scoped; the adapter separately enforces the
  finite `ownerBootstrapFiles` control-file allowlist. It reads no application
  source as part of this preparation.
- Retain only the private bounded preparation required for exact human review
  and recovery, under the existing private owner workflow. Do not put private
  bytes in public records, logs, Studio or model context. Subsequent source
  writes retain their separate exact-plan approval, Gary identity and human
  review/merge; a read token cannot authorize them.
- Qualification must cover private create/link through registration, setup,
  admission and manually authored reviewed source work, plus expired/revoked
  access, a foreign repository/account, changed visibility, lost acknowledgements
  and original-request recovery. Acceptance and runtime activation remain a
  later explicit batch step. Rollback disables the new read capability and
  revokes its credentials while preserving private drafts and receipts.

### Registration metadata — internal operational storage

The operator approved private-source support, including private listing metadata.
A direct provider read confirms that Workspace Governance, Console and Studio
are public repositories. Current Intake/Inventory writers publish repository
identity, names and responsibility text into Workspace Governance Git records.
Private runtime snapshot mounts are copies of that canonical source; they do not
make a public source publication private. The engine/tenant boundary is declared
but does not currently supply a separate private instance-record authority.

The operator selected installation-private operational storage for registration
records for both public and private projects. Reuse OOS orchestration and WGCF's
existing private database under Governance policy. Public repositories retain
software and shared contracts; Git connections manage project source. No separate
records Git repository, new service or installer is required. Accepted decisions
and durable internal receipts replace Git publication for these records; actual
code changes retain their source review controls.

The new authority contract is
[Internal operational records](https://github.com/mfshaf7/workspace-governance/blob/main/docs/instance-operational-records.md).
It is currently unpublished maintenance. Existing source-backed records and
pending reviews retain their original evidence and authority until explicit
migration. Setup, source authority and Console projections must consume the same
internal record before the complete route can be qualified.

Until that route is qualified and activated, private records must not enter a
public source review or commit. Private create/link history may stay in the
existing protected OOS custody store and remain visible in the Console. Do not
claim that these partial states establish active workspace registration.

### Unpublished source qualification checkpoint

The candidate now includes internal registration, owner-control inspection,
scoped authenticated checkout, active Inventory, ordinary Gary source authority,
and Delivery repository-readiness consumption. Repo Control uses the actual
current internal status, while the retained Git route remains separate. Isolated
tests cover original-request recovery and real Git source work. These source
checks do not activate live private development or qualify private Studio import.
The normal Console witness follows reviewed batch publication and exact composed
acceptance. Private Proposal/Studio/Catalog record migration remains later work.

Delivery's repository picker now searches the same current Registry instead of
a fixed example list in live mode. The bounded internal page and retained legacy
Inventory stay distinct. When more records match, narrow the search; a partial
page is not the whole register. Loading or failed reads cannot authorize a
selection. Repo Control passes its canonical repository key to Delivery, and
linking resolves current registration independently of the visible search page.
WGCF still checks actual current eligibility before any Catalog mutation/link.
