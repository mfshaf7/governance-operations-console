# Prototype source authoring

This is the primary Console procedure for the staged bounded app/design source
tool. It is source preparation, not an activated capability. Exact merged-source
Security acceptance and coherent Platform commissioning are still required.
Passing tests or seeing an authoring button does not qualify a product journey.

## Operator path after commissioning

1. Select the actual Studio Prototype, then open **Source Authoring** from the
   selected panel or Dashboard. The Dashboard launches the tool; its accepted
   cockpit and lifecycle controls remain separate.
2. Refresh retained requests first. Select an existing request to resume it;
   create a new bounded objective only for genuinely new source work. OOS
   verifies the actual Landing, registry/source snapshot and eligible custody.
3. Prepare source scope. Review the exact repository/provider/installation,
   branch, fetched base, Landing Unit, subject/operator, reviewer and expiry.
   Explicitly approve that digest. This permits bounded source actions and
   within-scope renewal only until the displayed deadline, not a new App grant.
4. Start the actual scoped session, then generate an app/design draft. The
   broker retains the original generation request and admitted context. No
   source is committed by generation, refresh or draft inspection.
5. Inspect every operation as inert source text. Accept only the inspected
   exact digest and current revision to create Gary's source commit. A changed
   draft must be inspected again; models cannot edit control-plane files.
6. Validate and publish the committed source. Open the retained PR, then use
   the separate accountable human exact-head approval and merge controls.
   Draft acceptance is not human PR approval or a CI result.
7. Close only after merged readback. OOS revokes the exact owned source scope
   and proves owned-resource retirement. Dirty, unique or unproven resources
   remain blocked rather than being discarded.

## Recovery

Reload uses retained OOS request, attempt and source-control state, not a
Console database. Interrupted generation resumes its original time, revision,
execution and context input. An uncertain apply uses accepted-action recovery,
never a replacement model draft. Publication/review/merge/close retries reuse
the original owner-retained command rather than a newly generated timestamp.

Source authorization displays the original issue/revoke operation and its
owner failure/next action and uncertainty deadline. Reconcile that same
operation; do not replace a possibly issued credential. Reads never renew.
Expired or stopped authorization requires exact predecessor revocation and a
fresh explicit successor approval for unchanged valid work. It does not require
a new Prototype, branch, ART story or approval deadline extension by implication.

Configured-live failure is unavailable, never a fixture success. Credentials,
private raw context and provider diagnostics remain outside browser and model
data. The existing verified Operator / Workspace owner server boundary and
caller attribution authorize mutations; browser-supplied identity is rejected.

## Separate downstream decisions and current limits

The same source tool offers trusted Studio Preview-profile preparation. Choose
that purpose before creating the immutable request and review the port, TTL,
support mode, activation intent and operator decision reference. The broker
derives the profile path and invokes the commissioned owner planner, not the
model. Inspect and accept its exact draft, then use the same validation,
Gary publication, human review, merge and cleanup controls. Neither a draft nor
an active-profile intent starts a Preview process.

Preview readback accepts only the paired `none`/`runtime-metadata-only` or
`prototype-local`/`browser-local` declarations, with synthetic/mock internal
review, read-only server methods and no external services or public ingress.
Browser-local data can survive server stop/restart. Runtime/profile proof is
not proof of browser persistence, client privacy or a hostile-script sandbox.
The new boundary still requires exact-source Security acceptance and coherent
commissioning; source tests do not activate it.

Source delivery is not Preview proof, Candidate promotion, Baseline approval,
Delivery ingress, graduation, product admission or application readiness.
Native Delivery-packet preparation is a separate purpose in this same source
tool. Supply typed work, resolved custody intent, existing evidence, rationale
and the operator decision reference. OOS rejects a Prototype without its real
accepted Baseline before source resources or authorization. Studio's existing
emitter derives and validates its actual Baseline digest and Git source/tree;
the browser cannot supply Baseline or Git evidence. Inspect and review the
emitted packet plus normal registry backlink through the same source path.
After merge, use the existing canonical packet and Prototype-to-Delivery
application control. Preparing the packet is not applying it to Delivery.

Selected durable-owner bootstrap/import and post-merge owner acceptance remain
part of the approved whole-path work, not capabilities this tool claims to have
completed. Source preparation still needs composed review, coherent activation
and normal Console operating proof.

The current bounded source adapter is Studio-incubated synthetic/mock work.
Public synthetic demonstration does not qualify private/client custody, every
toolchain, arbitrary source repositories, shared runtime or public hosting.
Shared ordinary-source authorization also serves real Delivery sessions. Its
prospective decision is retained by OOS before a session exists, and the
Console can recover that decision and its original source authorization after
reload. Start/continue and accepted-source recovery forward only the exact
source-intent reference separately from the unchanged business/model inputs.
These staged consumers still require composed review and operating proof.
